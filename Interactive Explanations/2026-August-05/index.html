Problem of the Day

Remove Methods
From Project LeetCode #3310

A project has n methods. One is the bug source.
Use BFS to find all suspicious methods — then decide: can we safely remove them?

⚡ Medium 🌐 Graph 🔍 BFS 📊 In-Degree 🦠 Infection Spread
01 The Problem
📖
What's the Problem?

You have n methods in a project, connected by invocation edges — method u calls method v. One method k is identified as the bug source. All methods reachable from k are suspicious.


But there's a catch: you can only remove the suspicious methods if no non-suspicious method calls a suspicious method. If any external dependency exists, you must keep everything!

🦠
The key challenge: After BFS marks all suspicious methods, check if any suspicious method still has in-degree > 0 from a non-suspicious caller. If so, removal would break the project — return all methods instead.

03 Intuition
🧠
Two-Phase Strategy

Think of it like contact tracing for a virus:

  • Phase 1 — BFS from bug source: Mark all reachable methods as suspicious. While doing this, decrement in-degree of neighbors (since suspicious→suspicious edges don't count as external deps).
  • Phase 2 — Check in-degrees: If any suspicious method still has inDegree > 0, it means a non-suspicious method calls it — removal would break the call chain!
  • Decision: If any dependency exists → can't remove → return all methods. Otherwise → safely remove suspicious methods.
💡
Why decrement in-degree during BFS? When we traverse edge sus → ngbr, we do inDegree[ngbr]--. This removes the "internal" edges. After BFS, if a suspicious node still has inDegree > 0, the remaining edges must come from outside the suspicious set.
04 Approach
🗺️
Step-by-Step Approach

1. Build adjacency list + in-degrees

Construct the directed graph from invocations. Track inDegree[v] for every node.

2. BFS from bug source k

Push k to queue, mark as suspicious. For each neighbor, decrement in-degree and mark suspicious if not already.

3. Check: can we remove?

Scan all nodes. If any sus[i] == true and inDegree[i] > 0 → a non-suspicious node depends on it → can't remove.

4. Build result

If can't remove → return [0, 1, 2, ..., n-1]. Otherwise → return only non-suspicious method IDs.

07 Full Code
C++ • solution.cpp 
// leetcode problem 3310 Remove Methods From Project
// https://leetcode.com/problems/remove-methods-from-project/

#include <iostream>
#include <vector>
#include <queue>
#include <algorithm>
using namespace std;

class Solution {
public:
    vector<int> remainingMethods(int n, int k,
            vector<vector<int>>& invocations) {

        vector<vector<int>> adj(n);         // adjacency list
        vector<int> inDegree(n, 0);          // in-degree count
        vector<bool> sus(n, false);          // suspicious flag

        for(auto &edge : invocations) {
            int u = edge[0], v = edge[1];
            adj[u].push_back(v);
            inDegree[v]++;
        }

        // BFS from bug source k
        queue<int> que;
        que.push(k);
        sus[k] = true;

        while(!que.empty()) {
            int curr = que.front();
            que.pop();
            for(int &ngbr : adj[curr]) {
                inDegree[ngbr]--;            // remove internal edge
                if(!sus[ngbr]) {
                    que.push(ngbr);
                    sus[ngbr] = true;
                }
            }
        }

        // Check: can we safely remove?
        vector<int> result;
        bool canNotRemove = false;
        for(int i = 0; i < n; i++) {
            if(sus[i] && inDegree[i] > 0) {
                canNotRemove = true;          // external dep!
                break;
            }
            if(!sus[i]) {
                result.push_back(i);
            }
        }

        if(canNotRemove) {                     // can't remove
            vector<int> vec(n);
            for(int i = 0; i < n; i++) vec[i] = i;
            return vec;
        }
        return result;                         // safe methods
    }
};

09 Complexity Analysis
📊
Time & Space Complexity
Time
O(n + e)
BFS visits each node & edge once.
Final scan is O(n).
Space
O(n + e)
Adjacency list + in-degree array
+ BFS queue + sus array.
🚀
This is optimal! We must look at every node and edge at least once. BFS gives us exactly O(n + e) — no wasted work. The in-degree trick avoids a second traversal.
10 Key Takeaways
✅
Remember These
  • BFS reachability is perfect for "infection spread" / "connected component" problems.
  • The in-degree decrement during BFS is the key trick — it separates internal vs external edges.
  • If any suspicious method has remaining in-degree → external dependency → can't remove.
  • This models a real-world scenario: removing buggy modules from a codebase without breaking callers.
  • Time complexity is O(n + e) — linear in graph size, which is optimal.
  • The pattern "BFS + in-degree check" appears in topological sort, dependency resolution, and package managers.
